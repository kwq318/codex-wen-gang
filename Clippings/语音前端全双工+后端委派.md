机制总览｜语音前端全双工，后端异步委派，结果回注会话

语音前端 + 后端委派

— · —

很多 Voice Agent 听起来「慢」，根因往往不是模型不够大，而是系统把听、想、说串在同一条阻塞链路上。用户一插话，整条链就得重来。

「语音前端 + 后端委派」要解决的，就是这件事：把实时交互和重计算拆成两条时间线。前端保证对话不断；后端负责推理和工具；两边用委派 ID 对齐。

01｜单链路为什么天然会卡

经典级联是 ASR → LLM → TTS。它清晰、好调试，但默认假设：一轮说完，再轮到系统。真实通话里，人会改口、会抢话、会说「嗯你查一下」。任何「等整轮结束」的设计，都会在这里暴露空白。

更关键的是：工具调用通常是秒级甚至十秒级，而口语反馈需要百毫秒级。把两者绑死，要么假回「好的稍等」却其实没在干活，要么干完活用户早换话题了。

原理一句话

交互延迟预算和任务延迟预算不是同一量级，所以不能共用一条阻塞路径。

02｜语音前端：全双工在管什么

![图片](https://mmbiz.qpic.cn/sz_mmbiz_jpg/xjdRN48U1EjhqkCpUgZib6YMiaTj0DATP6HFasibL2TQw74yymXx7EcRIzfibwXsnCL9KP3pYJ8icORt9RtBZTr1bCKHibiaews3crehOrE3wU2ibFo/640?wx_fmt=jpeg&watermark=1#imgIndex=1)

图1｜前端同时维持「听流」与「说流」，打断是一等公民事件

全双工不是营销词，它表示系统在播放语音时仍持续接收用户音频，并能判定「这是附和」还是「这是打断」。

前端真正负责的机制通常只有几类：

·端点与轮次：用户说完了吗？还是只是喘口气？

·打断（barge-in）：用户抢话时，输出音频如何立刻收敛。

·韵律与节奏：该停顿、该附和、还是该继续说。

·轻量理解：是否需要委派？关键词/意图是否命中？

注意边界：前端可以产出转写和口语回复，但不该独自扛长推理、复杂工具编排、权限审批。那些会拖垮实时性。

03｜核心机制：两条时间线

![图片](https://mmbiz.qpic.cn/sz_mmbiz_jpg/xjdRN48U1EiaGpNWBr95pNEqob96Uv9I9IiaLI3jOAZcCfx0IbxBW9tdRu6fTkue5z4x67cflTCSUSd3KEq5UJibfXyiarHDkEAmQ6fcmIaOia4Y/640?wx_fmt=jpeg&watermark=1#imgIndex=2)

图2｜语音时间线连续推进；任务时间线并行；靠委派 ID 对齐

拆开之后，系统里同时跑两条时钟：

·语音时间线：听、说、打断、回注后的口语组织。

·任务时间线：排队、执行、成功/失败、过期或取消。

委派发生时，前端不是「把麦克风交给后端」，而是发一个带 ID 的任务，自己继续维持会话。后端完成后，按同一 ID 把结论回注；前端再决定怎么说出口。

关键不变量

打断会改变语音时间线，但默认不自动取消任务时间线。是否取消，必须显式建模。

04｜三层职责怎么切

![图片](https://mmbiz.qpic.cn/mmbiz_jpg/xjdRN48U1EhyHr7fh8YctqVAHOyvm1gEVxZaczTKFb4KkxyibicDRlsm3DKXH5X06JHziasKR0H1tTO2XYsRdjoRzV3aKKXKGM3aNqYxcGvLHk/640?wx_fmt=jpeg&watermark=1#imgIndex=3)

图3｜前端层 / 委派总线 / 后端层

可以按职责切三层，避免「全能语音模型」吞掉业务：

·语音前端层：实时听写、打断、口语生成。

·委派总线：会话上下文切片、任务创建、结果回注、超时策略。

·后端层：更强推理模型、工具、CRM、知识库、审批流。

业界常见两种委派形态：托管后端（会话里直接指定一个推理模型）与客户端委派（你自己的 Agent/服务接任务）。机制相同，差别在「谁执行、谁管权限」。

05｜任务状态机：迟到结果怎么处理

![图片](https://mmbiz.qpic.cn/sz_mmbiz_jpg/xjdRN48U1EhJlibPElRKTpoOibdsz6rTWibicibibib881YJo3miaXWQeicYQTMpvJQdyZb0B4DL2icGRhUj4wruAIu5qjlu4PThRagC49T2ibYInDRoicw/640?wx_fmt=jpeg&watermark=1#imgIndex=4)

图4｜任务生命周期；打断可导向过期/取消

没有状态机，双时间线一定会乱。最少要覆盖：空闲 → 会话中 → 已委派 → 等待结果 → 已回注；以及旁路：已过期 / 已取消。

研发上最容易踩的三个坑：

·用户已换话题，旧查询结果仍被大声播报。

·打断只停了 TTS，后台还在写库，造成「说停了、事没停」。

·多次委派并发，回注顺序错乱，口语自相矛盾。

实用策略：回注前校验「委派是否仍对应当前话题」；过期结果只进日志或轻提示；需要副作用的工具默认要求确认或可回滚。

06｜对研发意味着什么

这不是换一个更甜的 TTS，而是换并发模型。你要同时观察：会话事件、委派事件、工具耗时、打断时刻。同一条链路用会话 ID + 委派 ID 串起来。

评测也要拆开：前端看首包时延、打断恢复、轮次自然度；后端看工具成功率、正确性、尾延迟。混成一个「好不好听」分数，会掩盖故障。

选型提醒

级联方案没有过时——日志清晰、合规好做。新范式适合强交互、强工具场景；两者可以并存，用场景切，不靠信仰切。

收束成一张心智图

语音前端保证「在场」；后端委派保证「办事」；委派 ID 保证两边还能对上话。搞懂这三件事，你就搞懂了这套机制的主干——其余都是协议细节和产品策略。
