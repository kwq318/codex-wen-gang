汽车工程师 座舱 *2026年9月14日 11:20*

> 先看两句话的区别：  
>   
> **"打开空调"** —— 这是一条命令。识别意图、执行动作、结束。  
> **"帮我点杯减脂咖啡，我半小时后到公司"** —— 这是一个任务。要选店、选品、算时间、下单、规划取餐路径。

前者是语音助手做了十年的事，后者才是 **Agent（智能体）** 。这两者之间的差距，就是这期要聊的工程代价。

---

## ▍一、从"一问一答"到"规划—调用—迭代"

传统语音助手是 **prompt-response** 模式，而 Agentic 流水线是这样一条链路：

| 环节 | 做什么 |
| --- | --- |
| **ASR** | 座舱麦克风音频 → 文字（含噪声抑制、唤醒词、端点检测） |
| **Orchestrator（编排器）** | **路由意图、维护会话状态、选择技能/工具、执行策略** |
| **LLM 推理引擎** | 分词、批处理、 **KV-cache 管理** 、硬件加速 |
| **AI 模型** | LLM / VLM，提供语言理解、总结、甚至舱内视觉理解 |
| **TTS** | 把结果转成自然语音（含适合驾驶的韵律） |

**关键的新增是那个 Orchestrator。** 它需要决定：这个请求该派给谁、超时怎么办、失败了怎么回退、 **以及——这个 Agent 到底被允许在车里改什么** 。

> **有没有 Orchestrator，是"语音助手"和"智能体"的分水岭。**

---

## ▍二、多 Agent 怎么协同：两个真实框架

复杂任务不可能由一个大模型包办，行业主流是拆成多个专职 Agent 协同。看两个已落地的框架：

**弋途科技的 MCP-Agent 框架**  
把 **续航检测、商户筛选、路径规划、支付** 拆成独立智能体，通过 **MCP 标准化协议** 互相协同。用户说"点杯减脂咖啡"，系统跑通从选品到下单到导航的全链路。

它还解决了多轮变更：点咖啡时从 **选品 → 修改杯型 → 调整取餐地址** ，靠上下文窗口优化 + 记忆模块承接， **无需重复解释背景信息** 。

**东软 NAGIC.AI**  
四个模块协同：  
\- **Router** ：解析模糊意图、分配对应场景 Agent  
\- **Memory** ：共享记忆池，实现跨 Agent 意图补全  
\- **Function Call** ：调用底层车机能力（导航、ADAS、座舱 IVI、多媒体）  
\- **HCP 异构计算平台** ：分层适配不同算力平台与系统（Linux / QNX / AutoSAR）

**两个框架的共同点很清楚：路由 + 记忆 + 工具链，三者缺一不可。** 没有路由就不知道派给谁，没有记忆就无法多轮，没有工具链就只能"说"不能"做"。

## ▍三、端云怎么分：一个 100 毫秒的答案

Agent 比传统助手重得多，全放端侧跑不动，全放云端又慢又怕断网。 **腾讯 2026 年发布的座舱智能体架构是个很好的参考：**

|  | 端侧 | 云端 |
| --- | --- | --- |
| 模型 | **0.8B 轻量化 VLM + 座舱世界模型** | 混元大模型 Hy3 preview |
| 指标 | **单帧编码延迟 <100 毫秒** | 强推理、长记忆、Agent 能力 |
| 职责 | 毫秒级环境感知， **弱网也能敏捷交互** | 复杂意图理解、多轮对话、服务生态调用 |

**这个分工的逻辑很清晰** ：端侧负责"感知现在"，云端负责"规划未来"。端侧小模型保证 **弱网甚至断网时依然可用** （呼应第 24 篇的端侧部署），云端大模型负责真正复杂的推理。

**记忆是 Agent 体验的核心** ：依托 **声纹 ID** 精准识别不同驾乘者，记住爸爸的导航习惯、妈妈的音乐偏好、孩子的故事喜好， **记忆召回率达 90% 以上** 。

## ▍四、三个真正难的工程问题

这部分是我最想聊的，因为它们 **在演示里看不出来，却在真实使用中决定成败** 。

**① 上下文共享（Context Sharing）**  
云端 Agent 介入时， **必须共享已有上下文** 。如果云端助手把用户刚说过的话再问一遍，体验直接崩掉。

反过来也一样：云端可能掌握车端没有的关键信息（比如"用户马上有个重要会议"），这时应该反过来约束车端—— **别在此时给驾驶员塞太多信息。**

**② 异步与透明性（最难的一条）**  
联网搜索和远程工具调用需要时间； **如果网络中断，派到云端的任务可能根本不会返回。**

所以车端 Agent 必须做到三件事：  
\- **跟踪异步工作负载的状态**  
\- **跟踪预期完成时间**  
\- **跟踪网络连接状态，并准备好回退机制**

> **用户点了杯咖啡，车进了隧道，10 分钟后出来——这时候车机该说什么？**
> 
> 是"还在处理"、还是"已下单"、还是"网络中断请重试"？这个看似小的交互，背后是一整套异步任务管理。

**③ 权限边界**  
Agent 在车里 **到底被允许改什么** ？这是 Orchestrator 的核心职责之一，也是安全问题。

我的判断很明确： **娱乐、导航、空调这类可以自主；涉及车辆控制（车窗、驾驶辅助、动力）的，必须显式确认，且要有可撤销机制。**

## ▍五、隐私：Agent 必须跑在"沙箱"里

Agent 能调用的服务越多，滥用风险越大。行业目前的做法是两层防护：

\- **数据脱敏脱密** ：车内摄像头等传感器数据的使用前提是脱敏（就像"守卫模式"自动模糊人脸和车牌）  
\- **沙箱隔离** ： **智能体运行在沙箱里** ，数据操作被严格限制在合理范围内

这一条和第 25 篇的数据合规是同一件事的两个面： **法规管"能不能采"，沙箱管"采了能怎么用"。**

---

> **工程师私货**  
> 
> Agent 上车这一年，我最深的感受是： **它把"体验问题"变成了"系统问题"。**  
> 以前语音助手不好用，多半是识别率或时延的问题——优化模型就能改善。现在 Agent 不好用，可能是任务拆错了、路由选错了、异步状态没管好、上下文没传过去、 **或者干脆是某个外部服务挂了** —— **而这些都是车厂无法完全掌控的。**  
> 三条判断：  
> **① 先定义"不能做什么"，再定义"能做什么"。** Agent 的能力边界必须是 **白名单** 而不是黑名单。我在权限评审上花的时间，比在功能开发上还多，这是值得的。  
> **② 异步体验是护城河。** 大家都做得了"同步任务"，但 **"网络断了怎么办""任务要跑 3 分钟怎么告诉用户""失败了怎么优雅回退"** ——这些细节才是真实差距。  
> **③ 别为了 Agent 而 Agent。** 有些需求用一条规则就能解决（比如"每天 8 点打开座椅加热"），非要套个 Agent 只会更慢更贵更不可控。 **能用确定性逻辑解决的，不要交给概率模型。**  
> 最后一句： **第 03 篇我讲过语音的工程真相；这一篇是它的续集——当助手学会"办事"，工程复杂度不是加一点，而是换了一个量级。**
