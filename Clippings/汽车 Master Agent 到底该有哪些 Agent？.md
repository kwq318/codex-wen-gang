产品小学生 座舱 AI 研习社 *2026年9月16日 07:28*

过去两年，几乎每家车企都在讲"大模型上车"。但真正落到工程上，绝大多数项目卡在同一个地方： **把大模型当成了一个更聪明的语音助手，而不是一套调度整车能力的操作系统** 。

结果就是那个熟悉的场面——demo 里"打开空调"很惊艳，量产后用户说三句话有两句听不懂；智驾团队和座舱团队各做一个大模型入口，互相不通气；一个功能出问题，没人知道是意图理解错了、路由发错了、还是下游服务超时了。

问题的根子不在模型，在架构。 **一辆车上不该有一堆平级的 Agent 各自抢麦，而应该有一个 Master Agent 承担"整车智能中枢"的角色，其余 Agent 按域分层归属，通过明确定义的契约、总线和权限模型协同。**

这篇文章我会假设自己是一家中国新能源车企的智能化负责人，把这套东西从头搭一遍。不讲愿景，只讲怎么落地：分几层、有哪些 Agent、谁管谁、消息长什么样、时延预算怎么分、出问题怎么兜。

> **先给结论。** Master Agent 不是"最大的那个 Agent"，它是 **唯一持有全局上下文和仲裁权的调度者** 。它自己不执行任何具体能力，也不能指挥安全相关的执行器——它只做四件事：理解用户到底要什么、决定交给谁、协调多方按什么顺序做、以及在任何一环失败时决定怎么退。

## 01为什么必须有 Master Agent

从"多入口混战"到"单一中枢"的三个必然理由

先说清楚不做 Master Agent 会发生什么。这不是理论推演，是行业里已经反复出现过的三类事故。

### 理由一：用户的一句话，天然是跨域的

"我有点冷，待会儿要去接孩子，顺路找个能吃饭的地方充电。"

这一句话里包含：空调调节（车控域）、日程与联系人（个人域）、导航目的地推理（地图域）、补能规划（能源域）、POI 筛选（生态服务域）。五个域，五套系统，如果没有一个统一的意图理解和任务分解层，只能靠规则硬编码去撞——而用户的表达方式是无穷的。

**单一入口的价值不在"少一个按钮"，而在于它是唯一有资格做跨域任务分解的地方。**

### 理由二：能力越多，冲突越多，必须有人仲裁

车上同时存在这些"想说话"的角色：智驾要提示接管、电池管理要警告低温、导航要播报路口、来电要响铃、儿童座椅检测到遗留、音乐正在高潮部分。

它们全都合理，但不能同时发生。谁优先、谁被压制、谁延后到下一个安全时机、谁降级成只亮灯不出声—— **这是一个仲裁问题，必须有唯一的裁判** 。分散在各域自己判断，必然出现"三个语音一起播"和"最重要的那条被音乐盖住"。

### 理由三：责任链必须可追溯

车是安全产品。任何一次交互，事后都要能回答：用户说了什么、系统理解成了什么、路由给了谁、下游返回了什么、最终做了什么动作、为什么。

没有中枢就没有统一的 trace，出问题只能各团队互相甩锅。 **Master Agent 的一个隐性但关键的产出物，是一条贯穿全链路的可观测轨迹。**

但要立刻划一条红线

Master Agent 是 **调度中枢，不是控制中枢** 。它绝对不能进入功能安全的执行链路——不能改变转向、制动、驱动的指令，不能覆盖智驾系统的决策，不能绕过底层的安全监控。这条边界我在第 04 章会用"三种归属关系"讲透，它是整个架构里最不能妥协的部分。

## 02产品架构：五层，一根总线，两条安全隔离带

先把骨架立起来，再往里填 Agent

我把整车 Agent 体系分成五层。分层的原则很朴素： **每一层只对上一层暴露契约，不暴露实现** 。这样座舱换供应商、智驾换算法版本、大模型换底座，都不会引发全栈重写。

![图片](https://mmbiz.qpic.cn/sz_mmbiz_png/Il8Q58ED4HMqerBicOwNJDoNsdxgVaJYkhtAzeIKqDaKZoFYibicViaibRicohIvYpdZ4tf8zaZIYz890n3nV45IRREzgbGRAWD4ibAacv4LPOR4Lg/640?wx_fmt=png&from=appmsg&watermark=1#imgIndex=0)

五层之间只通过契约通信。L2 到 L3 走统一消息总线（AIB），L3 到 L4 走强类型工具调用。两条红色虚线是硬边界：Agent 永远不能跨过它们直接碰功能安全域。

### 逐层说清楚每层的职责边界

| 层 | 唯一职责 | 绝对不做 | 典型失败模式 |
| --- | --- | --- | --- |
| L1 交互感知 | 把物理世界变成结构化事件，带上"谁、在哪、什么状态" | 不做语义理解、不做决策 | 声源定位错，把副驾的话当主驾指令执行 |
| L2 Master | 理解、规划、路由、仲裁、兜底、留痕 | 不执行具体能力，不碰安全执行器 | 意图理解正确但路由到错误的域，或多域任务只完成一半 |
| L3 域 Agent | 在本域内做专业决策，把领域知识封装起来 | 不跨域直接调用其他域 Agent | 域间私自"抄近路"通信，形成隐形耦合，出问题无法定位 |
| L4 工具 | 执行原子操作，保证幂等与可回滚 | 不含业务判断，不做重试策略 | 非幂等接口被重试两次，空调设了两遍温度或订单下重了 |
| L5 基础 | 提供算力、模型、数据闭环、安全合规 | 不感知业务语义 | 模型热更新后未回归，线上意图分布突变 |

关于那根总线（AIB）的一个关键设计

域 Agent 之间 **禁止直接点对点调用** 。所有跨域协作必须经过 Master 编排，或以"事件发布—订阅"的方式在总线上广播。这一条会被工程师抱怨"绕、慢"，但它换来的是：任何一次跨域行为都有唯一的编排记录，可回放、可归因、可灰度。我宁愿多付 10 毫秒，也不要一个三年后没人能理清调用关系的系统。

## 03功能架构：到底该有哪些 Agent

25 个域 Agent 的完整清单，以及为什么是它们

这是全文最实用的一节。我按五个域列出 25 个 Agent，每个都给出它的 **输入、决策权、可调工具、以及最容易被忽略的边界** 。

划分 Agent 的标准只有一个： **它是否拥有一套外人不该知道的领域知识** 。如果两个能力共享同一套知识和状态机，就该合成一个 Agent；如果一个"Agent"只是若干 API 的透明转发，它就不该是 Agent，而应该降级成 L4 的工具。

### 座舱域 · 5 个 Agent

座舱是用户感知最强的域，也是最容易堆砌功能的域。这里的关键是 **把"表达"和"执行"分开** 。

| Agent | 核心职责 | 决策权边界 |
| --- | --- | --- |
| **语音交互 Agent** | ASR 纠错、多轮澄清、指代消解、TTS 情感与语速、打断与续接 | 可自主决定"是否需要问一句"；不可自主执行车控 |
| **车控执行 Agent** | 空调、座椅、车窗、氛围灯、后视镜等舒适件的组合控制与状态记忆 | 可组合执行舒适件；行车中禁止操作影响视野与安全的部件 |
| **影音娱乐 Agent** | 音源选择、音效场景、播放列表推理、游戏/影院模式的进入与退出条件 | 可自主切换音效；进入影院模式必须校验车辆静止且驻车 |
| **多屏多音区 Agent** | 内容在主屏/副驾屏/后排屏之间的流转，四音区独立声场与隐私 | 可自主分配屏与音区；不可把主驾必需信息移出主驾视野 |
| **健康关怀 Agent** | DMS 疲劳/分心、儿童遗留、空气质量、久坐提醒、晕车抑制 | 可主动发起干预；生理数据不出车且不做医疗诊断结论 |

一个容易踩的坑

很多团队把"语音"做成了一个什么都管的巨型 Agent——它既理解意图，又直接调车控 API，还自己决定播什么。 **这等于把 Master 的职责下沉到了座舱域** ，结果是智驾和能源域的能力永远接不进来，因为入口不在中枢手上。语音 Agent 应该只负责"听清楚、说明白"，理解与调度归 Master。

### 智驾域 · 5 个 Agent

智驾域是整套架构里权限最特殊的域： **它可以向 Master 上报和请求，但 Master 对它只有"建议权"，没有"指令权"** 。

| Agent | 核心职责 | 决策权边界 |
| --- | --- | --- |
| **驾驶意图协商 Agent** | 把"开快点""别老让人""在下个路口靠边"翻译成智驾可接受的风格参数与请求 | 只产生 **请求** ，由智驾规控自行裁决是否采纳并返回理由 |
| **路线策略 Agent** | 基于路况、能耗、智驾可用里程占比、用户偏好，做路线与车道级策略推荐 | 可推荐；变更进行中的路径须用户确认或满足预设自动条件 |
| **泊车与召唤 Agent** | 车位记忆、泊入泊出、远程召唤的任务编排与异常中止 | 可编排低速场景；全程要求人在环或视线内，超时即中止 |
| **接管提示 Agent** | 生成分级接管提示（视觉/听觉/触觉），并保证提示不被任何娱乐内容压制 | **拥有最高播报优先级，Master 不得压制** |
| **场景解释 Agent** | 用自然语言解释"我为什么减速""为什么不变道"，提升信任与可解释性 | 只读智驾状态做解释；解释延迟不得影响控制主循环 |

这是整篇文章里我最想强调的一句

**大模型永远不进入智驾的控制闭环。** 智驾域 Agent 的作用是"翻译用户意图"和"解释系统行为"，它把请求递给规控，规控按自己的安全逻辑裁决。任何"让大模型直接给出转向角/加减速"的设计，都无法通过功能安全论证，也无法在事故中说清责任。这不是保守，是行业底线。

### 能源与车辆域 · 5 个 Agent

这个域是中国新能源车最能建立差异化的地方，因为 **补能焦虑是真实痛点，而它需要跨域协同才能解决** 。

| Agent | 核心职责 | 决策权边界 |
| --- | --- | --- |
| **补能规划 Agent** | SOC 预测、充电站筛选（功率/排队/价格/品牌）、多段路线的补能点编排、到站预热 | 可自主插入补能点建议；实际改变导航须用户确认 |
| **电池健康 Agent** | SOH 评估、充放电习惯建议、低温衰减解释、极端工况预警 | 可给建议与预警；不可擅自限制用户可用功率 |
| **热管理 Agent** | 协调座舱舒适、电池温控、快充预处理三者之间的能量分配 | **与座舱域天然冲突，冲突由 Master 按策略仲裁** |
| **故障诊断 Agent** | DTC 归因、症状问答、严重度分级、是否可继续行驶的判断建议 | 可给分级与建议；安全相关判定以整车控制器结论为准 |
| **OTA 升级 Agent** | 升级窗口选择、依赖校验、失败回滚、变更内容的人话解释 | 可选择时机；升级必须用户授权且满足静止/电量条件 |

### 生态服务域 · 5 个 Agent

这个域的特点是 **大量依赖外部三方，因此它是超时和失败的高发区** ，兜底设计要格外重。

| Agent | 核心职责 | 决策权边界 |
| --- | --- | --- |
| **地图导航 Agent** | 模糊目的地推理（"上次那家""孩子学校"）、途经点、路况改道 | 可推理候选；多候选必须让用户选，不做静默假设 |
| **生活服务 Agent** | 餐饮、停车场、洗车、酒店的检索、比较与预约 | 可检索比较；下单前必须明确确认 |
| **通讯社交 Agent** | 来电与消息的播报、语音回复、会议接入、行程共享 | 可播报摘要；隐私内容在有他人时降级为"有新消息" |
| **车家互联 Agent** | 回家/离家场景联动，与家居平台的状态同步 | 可执行预设联动；新增设备控制须一次显式授权 |
| **支付履约 Agent** | 充电、停车、加油的无感支付与凭证管理 | **任何扣款须强确认或在预设免密额度内，且必须可追溯** |

### 用户与运营域 · 5 个 Agent

这个域常被忽略，但它是 **让整套系统随时间变聪明的关键** ——没有它，你的 Agent 上市即巅峰，之后只会慢慢腐化。

| Agent | 核心职责 | 决策权边界 |
| --- | --- | --- |
| **用户画像 Agent** | 多用户识别、长期偏好沉淀、家庭成员与角色区分 | 可沉淀偏好；跨用户数据严格隔离，可一键清除 |
| **售后服务 Agent** | 保养提醒、预约、道路救援、维修进度、备件查询 | 可预约与派单；费用相关须用户确认 |
| **用车教练 Agent** | 新功能引导、能耗驾驶建议、隐藏功能发现、按需微教程 | 可主动推荐；同一建议不得重复骚扰（有频控） |
| **权益商城 Agent** | 会员权益、订阅功能、积分与充电权益的匹配与提醒 | 可提醒； **严禁在驾驶中做营销打扰** |
| **反馈闭环 Agent** | 捕获"这不是我要的"、自动打标、回流到数据闭环与评测集 | 可自动采集；上传须匿名化并遵守用户授权 |

25 个不是拍脑袋定的

判断标准是" **能不能独立评测** "。每个 Agent 都必须有自己的评测集和成功率指标。如果你为某个 Agent 写不出 50 条独立的验收 case，说明它没有独立的领域知识，应该并入邻近 Agent。这个标准非常好用，能砍掉大量为了 PPT 好看而存在的"Agent"。

## 04归属关系：三种关系，不是一种

"Master 管所有 Agent"是错的，管法有三种

很多架构图画成一棵树：Master 在顶上，箭头指向所有子 Agent。这张图，太粗糙—— **它把三种性质完全不同的关系画成了同一根线** 。

在真实的车上，Master 与子 Agent 之间存在三种关系，权限完全不同：

### 关系一：指令式归属（Command）— 座舱、生态、运营

Master 下发任务，子 Agent 必须执行并回报结果。这是最常见的关系，适用于 **不涉及安全、可回滚的能力** 。

- Master 说"把主驾温度调到 24 度"，车控 Agent 就执行。
- 失败要报错误码，不能静默失败。
- Master 拥有取消权：任务进行中可以中止。

### 关系二：协商式归属（Negotiate）— 智驾、能源

Master 只能 **提出请求** ，子 Agent 按自己的安全与领域逻辑裁决，可以拒绝，但必须给出理由。

- Master 说"用户希望开快一点"，智驾 Agent 回"当前限速 80、前方施工，不采纳，理由码 `SPD_LIMIT_CONSTRAINT` "。
- Master 拿到理由后，负责把它翻译成人话告诉用户—— **这是"拒绝"能变成好体验的关键** ：用户不怕被拒绝，怕的是没反应。
- Master 没有强制权，也不能重试绕过。

### 关系三：上报式归属（Report / Interrupt）— 安全类

子 Agent **主动上报，且享有不可压制的优先级** 。Master 在这条关系里的角色反过来了：它不是指挥者，而是"让路者"。

- 接管提示 Agent、儿童遗留检测、电池热失控预警属于这一类。
- 它们上报时，Master 必须立即挂起当前所有任务、静音娱乐、清空屏幕次要信息。
- **Master 唯一的动作是让路和记录，没有任何裁量空间。**

| 关系类型 | 适用域 | Master 权限 | 子 Agent 权限 | 冲突时谁赢 |
| --- | --- | --- | --- | --- |
| Command 指令 | 座舱 / 生态 / 运营 | 下发、取消、超时重试 | 执行、报错 | Master |
| Negotiate 协商 | 智驾 / 能源 | 请求、查询、接收理由 | 裁决、拒绝、给理由 | 子 Agent |
| Report 上报 | 安全相关 | 仅让路与留痕 | 无条件抢占 | 子 Agent（绝对） |

### 权限矩阵：把"谁能干什么"写成配置

这三种关系不能靠代码里的 if-else 实现，必须做成 **可审计的声明式配置** 。这样安全团队可以直接 review 这张表，而不用读代码。

![图片](https://mmbiz.qpic.cn/sz_mmbiz_png/Il8Q58ED4HM3XNWzP37TVdbtU0W4dIWR60iaiaiaJYwdLQ7zsc28ibFbzu6iaic7xlmK0dV5YDz3WUTyCAgajGWuGenjch5ccoFIRTAVVHkkiakXG8/640?wx_fmt=png&from=appmsg&watermark=1#imgIndex=1)

为什么 `forbidden` 字段比 `allowed` 更重要

白名单会随着功能迭代不断变长，总有人为了赶排期偷偷加一项。黑名单（尤其是安全相关的 `forbidden` ）应该 **由安全团队单独持有变更权，任何 PR 改动它都强制触发安全评审** 。这是把架构约束变成工程约束的唯一可靠办法——靠文档和口头约定，三个版本后一定失效。

## 05场景模拟：四个真实场景走一遍全链路

架构好不好，只能用场景验证

下面四个场景我按难度递增排列。每个都标注了 **哪些 Agent 参与、以什么关系参与、在哪一步可能失败** 。建议对照第 02 章的架构图看。

### 场景一：跨域复合指令（最典型的"Master 存在的理由"）

> 用户（主驾，行车中，SOC 28%）："我有点冷，待会儿要去接孩子，顺路找个能吃饭的地方充电。"

![图片](https://mmbiz.qpic.cn/sz_mmbiz_png/Il8Q58ED4HN8v9ggUq9gbxEpbDa1aXZyKxcUs9q2eV6ia4Wf1RbqBJZjrh7U7PsvFa0qQPbqZiaxicY3OX1ONUs2Fickno5P5ISFqiaw7ERwMNEY/640?wx_fmt=png&from=appmsg&watermark=1#imgIndex=2)

这个场景里有 **三个只有 Master 能做的判断** ，值得单独指出：

1. **识别依赖关系并决定并行/串行。**
	调温度不依赖任何东西，所以立刻做——用户在 430ms 内就感受到系统响应了，剩下 2 秒的规划时间他不会觉得慢。这是体感设计，不是技术细节。
2. **判定"必须确认"。**
	改路径和让用户等 12 分钟都是有代价的动作，不能静默执行。这个判断规则属于 Master 的安全网关，不属于任何域。
3. **约束选项数量。**
	行车中最多 2 到 3 个选项，且必须能纯语音完成选择。域 Agent 只管返回候选，"怎么呈现给行车中的用户"是 Master 的事。

### 场景二：安全打断（上报式关系的实战）

> 用户正在用语音订咖啡，系统正在播报订单确认，此时智驾请求接管。

![图片](https://mmbiz.qpic.cn/sz_mmbiz_png/Il8Q58ED4HMXElW9JvljngRxibw4JK7rc51hCNfhzDIJguImeMDYz1KbGkpM7Z9DjvUhwLqJ7cfxbe42fibdgjTohyx3IpKQhWPOqyicJxjQGA/640?wx_fmt=png&from=appmsg&watermark=1#imgIndex=3)

这里有个非常容易做错的细节

被打断的任务应该 **挂起而不是取消** ，但恢复时 **绝不能自动继续** 。我见过的错误实现是"安全事件结束后自动把订单提交了"——用户刚经历一次接管，注意力完全不在咖啡上，这时候静默下单是很糟糕的体验，甚至是资金风险。 **挂起、等安全、轻提示、由用户重新发起** ，这四步的顺序不能变。

### 场景三：主动服务（Master 自己发起，而非用户触发）

> 周五 17:40，SOC 19%，用户刚上车，导航历史显示他每周五这个时间回父母家（往返 96km）。

![图片](https://mmbiz.qpic.cn/sz_mmbiz_png/Il8Q58ED4HOQ0uKJjXmWfrCvPZJaZmYg8LS3ebnicGwyaINruakoR614vnribQquQgeCb7p0uVsFicAYdDLepUpHwyEIZukG2xP98uOu7uhytM/640?wx_fmt=png&from=appmsg&watermark=1#imgIndex=4)

**主动服务是最能体现产品力的部分，也是最容易变成骚扰的部分。** 这四道闸门我建议做成 Master 的强制流程，任何域 Agent 想主动发声都必须过闸——包括营销类。第 04 章权益商城 Agent 那条"严禁驾驶中营销"，就是靠闸门②落地的。

### 场景四：多用户冲突（副驾和主驾要求相反）

> 主驾说"关窗，太吵了"，几乎同时副驾说"开点窗，我有点闷"。

![图片](https://mmbiz.qpic.cn/sz_mmbiz_png/Il8Q58ED4HMicxN2mV94KW9synAHyEjVbOXgFQH8Iv6NhbjepFK0vcMBeONaQkseVBqIqJhOicnWu6agWbib0DQuGI2MoicWkQGF8Znic0fsLDMw/640?wx_fmt=png&from=appmsg&watermark=1#imgIndex=5)

能做到分区应答，靠的是 L1 的声源定位和 L3 的多音区 Agent。 **但"先尝试分区满足，再考虑优先级压制"这个规则顺序，必须写在 Master 的仲裁链里** ——如果规则顺序反了，副驾的诉求会被永久忽略，这在家庭用车场景里是很大的体验缺口。

## 06数据流转：消息契约、上下文栈、时延预算

架构的成败在这一章，因为这是唯一无法靠 demo 蒙过去的部分

前面几章讲的是"谁做什么"。这一章讲"数据长什么样、怎么流、多久必须流完"。 **我的经验是：Agent 体系的量产失败，九成不是模型不够强，而是消息契约没定死、时延预算没分配、状态回流没做全。**

### 一、消息契约：Master 下发给域 Agent 的任务包

这个结构体是整个系统的枢纽，值得逐字段设计。我用一个真实的补能规划任务作例子：

![图片](https://mmbiz.qpic.cn/mmbiz_png/Il8Q58ED4HOz7UnYSzZHEwyWLNygfHiaSDMqeJ73xCdJLSn3ZJartaEGZyRnoChHBC3Hd0nug1h3aMEgU6AxgD3IndS2UUTPsf1VBXv1iaaT0/640?wx_fmt=png&from=appmsg&watermark=1#imgIndex=6)

四个字段值得特别说明，它们是新手最容易漏掉的：

- **`relation`**
	：把第 04 章的三种关系显式写进消息头。域 Agent 收到 `negotiate` 就知道自己有拒绝权，收到 `command` 就知道必须执行或报错。 **不要让这个语义靠约定** ，要让它在报文里可见、可断言、可测试。
- **`context_slice`**
	：只切必要的上下文。全量下发看起来省事，实际上三个恶果——隐私面扩大、token 成本翻倍、单测无法构造。 **切片本身就是一种接口设计** ：域 Agent 声明自己需要哪些字段，Master 按声明裁剪。
- **`budget.deadline_ms`**
	：每个任务下发时就带死线。没有死线的异步调用，最终一定会有一次挂死在生态服务的三方接口上。
- **`fallback`**
	： **兜底方案在下发时就声明，而不是出错后临时决定。** 这是我最想推荐的一个实践——它把"兜底"从事故处理变成了架构的一部分，且可以在仿真环境里主动注入故障来验证。

#### 域 Agent 的回包：结果、理由、置信、以及"我没做到什么"

![图片](https://mmbiz.qpic.cn/sz_mmbiz_png/Il8Q58ED4HPXHaYjmMTmakDMXfKiaJTXicCXEEnib70ib4HcWNibziccOia89IaVHYf5DWfvL0Y5oiap8n5OFribPbYxianCLd5UnpHgmYQmChXG6KPH4/640?wx_fmt=png&from=appmsg&watermark=1#imgIndex=7)

`reason_code` 与 `reason_nl` 必须成对出现

机器码给监控和归因用（可以做成看板、可以告警、可以按码统计失败分布），人话给用户用（Master 拿去组织回复）。 **只有机器码，用户听不懂；只有人话，你的线上问题永远统计不出来。** 我建议在 CI 里加一条断言：任何非 `success` 的回包，两个字段都不能为空。这条规则成本极低，但对量产后的运维质量影响巨大。

### 二、上下文栈：Master 的核心状态

Master 要维护一个分层的上下文，不同层的生命周期完全不同。 **混在一起是灾难** ——最常见的表现是"用户下车再上车，系统还在追问上次的问题"。

| 层级 | 内容 | 生命周期 | 存储位置 | 清除时机 |
| --- | --- | --- | --- | --- |
| **瞬时槽位** | 当前多轮的待填参数、指代对象、待确认项 | 秒级 | 内存 | 任务完成 / 超时 30s / 话题切换 |
| **会话上下文** | 本次行程的对话历史、已执行动作、被挂起任务 | 本次上车 | 端侧内存 | 下电后 15 分钟 |
| **车辆实时态** | SOC、车速、挡位、座舱状态、网络质量 | 持续刷新 | 共享内存快照 | 不清除，只更新 |
| **用户长期记忆** | 偏好、常去地点、习惯时段、称呼方式 | 跨行程持久 | 端侧加密 + 云端可选 | 用户主动清除 / 账号解绑 |
| **领域知识** | 车辆手册、功能说明、故障码库、服务网点 | 版本级 | 端侧 RAG + 云端全量 | 随 OTA 更新 |

被中断任务的挂起栈要单独说一下。它需要三个字段： **挂起原因、挂起时的完成进度、恢复条件** 。恢复条件不能只写"安全事件结束"，还要包含时间窗（超过 2 分钟就不要再提了）和场景约束（用户已经在做别的事就不要打断）。场景二那句"要继续吗"之所以恰当，是因为它同时满足了这三个条件。

### 三、时延预算：把 800 毫秒拆到每一层

用户对车机响应的容忍度是有硬阈值的。我用的三条线是： **500ms 内感觉"跟手"，800ms 内可接受，1.5 秒后开始怀疑系统没听见** 。所以时延不是"优化目标"，是 **必须自上而下分配的预算** 。

![图片](https://mmbiz.qpic.cn/sz_mmbiz_png/Il8Q58ED4HPr7JuqSmHzgZQpXfF3JEFjASuSZ4Meb0E9UdGh9SBs09t1AreKJnN0zrNN1C0nicCU2HdhWhsuqicQIL4AY7b2F4w9YicAhw8StY/640?wx_fmt=png&from=appmsg&watermark=1#imgIndex=8)

路由仲裁始终是最薄的一段（20 到 60ms）——这是 Master 存在的代价，它换来的是跨域能力和统一兜底。真正的大头永远在域 Agent 执行和意图理解上。

| 阶段 | 端侧直达 | 端云协同 | 云端复杂规划 | 压缩手段 |
| --- | --- | --- | --- | --- |
| ASR 与端点检测 | 120 | 150 | 150 | 流式 ASR，边说边识别；VAD 提前收尾 |
| 意图理解 | 80 | 260 | 420 | 端侧小模型先判"是否高频简单指令"，命中即不上云 |
| 路由仲裁 | 20 | 40 | 60 | 权限矩阵预编译成查表，不做运行时推理 |
| 域 Agent 执行 | 150 | 420 | 780 | 并行下发；三方接口强制超时；结果预取与缓存 |
| TTS 首字 | 130 | 180 | 190 | 流式合成；先播确定的前半句，后半句边算边补 |
| **合计** | **500** | **1050** | **1600** | — |

1600ms 怎么可能可接受？答案是"分段应答"

复杂规划确实要 1.6 秒，但用户不需要等 1.6 秒才听到声音。 **Master 在 300ms 时就应该先出一句"我看一下"或"稍等，在找顺路的充电站"** ，然后在结果到达时接着说。这叫分段应答，它把"等待"变成了"对话"。

这也是为什么 **Master 必须掌握 TTS 的编排权** ——如果每个域 Agent 自己控制播报，就不可能实现这种跨域的分段。这是我在第 03 章强调"语音 Agent 只负责听清说明白"的深层原因。

### 四、端云路由：什么留在车上，什么必须上云

中国的路况和网络现实决定了 **端侧必须能独立完成一套完整闭环** ——地库、隧道、山区、跨省高速，断网是常态而非异常。

| 能力 | 部署 | 理由 | 断网表现 |
| --- | --- | --- | --- |
| 唤醒 / ASR / 车控意图 | 纯端侧 | 高频、低复杂度、安全相关、必须永远可用 | 完全正常 |
| 座舱设备控制 | 纯端侧 | 不依赖外部数据 | 完全正常 |
| 车辆知识问答 | 端侧 RAG | 手册与故障码可完整下发到车 | 完全正常 |
| 导航与 POI | 端云协同 | 需实时路况，但离线地图可兜底 | 降级：离线地图 + 缓存 POI |
| 补能规划 | 端云协同 | 需实时桩态，但缓存站点可兜底 | 降级：最近自营站，不保证可用 |
| 跨域复杂规划 | 云端为主 | 需大模型长链推理 | 降级：拆成单域指令逐条确认 |
| 生活服务与支付 | 纯云端 | 本质是在线交易 | 不可用，明确告知并建议稍后 |

路由决策本身要在 **20ms 内** 完成，所以它 **不能是模型推理，必须是查表** 。表的输入是意图类型、网络状态、SOC、安全等级；输出是执行位置和降级路径。这张表随 OTA 更新，但运行时是纯静态查询。

## 07优先级仲裁：Master 最难的一件事

同一时刻十件事都想说话，只能有一个说得出口

仲裁做不好，用户的感受是"这车很吵但没重点"。仲裁做好了，用户的感受是"它知道什么时候该说话"—— **后者是高端智能座舱和堆料座舱的真正分水岭** 。

仲裁不能靠一个简单的优先级数字，因为 **同一个事件在不同场景下的优先级是不同的** 。补能提醒在静止时很有价值，在接管过程中就是干扰。所以它必须是一张二维矩阵：事件类型 × 当前场景。

### 仲裁的四条规则，按顺序执行

1. **安全抢占。**
	得分 100 的事件直接抢占，跳过队列，不等当前播报结束。这一条没有例外，也不可配置。
2. **同类合并。**
	1.5 秒窗口内的同类事件合并为一条。"前方 300 米右转"和"前方 200 米右转"只播后者，不要连播两遍。
3. **低分延后而非丢弃。**
	得分低于当前场景阈值的事件进入延后队列，等到场景切换（比如停车了）再检查是否还有价值。 **关键是要带有效期** ——过期的提醒不如不提。
4. **通道降级。**
	不该出声的不代表不该出现。得分不足以获得语音通道的事件，降级为屏幕角标或氛围灯，不打断听觉。 **这一条是提升"不吵"体感的最有效手段。**

一个反直觉的建议

不要把这张矩阵交给算法学习。 **它必须是人工确定、显式配置、版本可追溯的。** 原因很简单：安全相关的优先级不能由数据分布决定，而且事故复盘时你必须能指出"当时生效的是哪个版本的哪一行"。可以用数据来发现"这一行配得不合理"，但修改必须是人工的、走评审的。

## 08兜底：五层降级，一条都不能少

大模型上车最大的风险不是不够聪明，是不确定

传统车机的失败模式是确定的：按了没反应，用户再按一次。 **Agent 系统的失败模式是不确定的** ——它可能理解错、可能编造、可能执行一半、可能超时后卡住、可能三方接口返回了脏数据。用户无法预测，因此也无法自己绕过。

所以兜底不是"加个 try-catch"，而是 **一套贯穿五层的降级体系，每层都有明确的触发条件、降级动作和用户可感知的表达** 。

### 第一层：输入侧兜底 —— 没听清就别猜

| 触发条件 | 降级动作 | 对用户的表达 |
| --- | --- | --- |
| ASR 置信度 < 0.6 | 不进入意图理解，直接请求复述 | "这句没听清，再说一遍？" |
| 意图置信度 0.5 至 0.75 | 带假设的确认，而非开放式提问 | "你是说把温度调高吗？"（可一键确认） |
| 意图置信度 < 0.5 | 给出 2 个最可能候选，不猜 | "是想调空调，还是开窗？" |
| 多轮澄清已 2 次仍未收敛 | **停止追问**  ，转交人工或图形界面 | "我可能没帮上，直接在屏幕上选一下？" |
| 声源定位与内容矛盾   （后排要求改主驾设置） | 需主驾确认后才执行 | 向主驾确认："后排想把主驾温度调低，可以吗？" |

**"追问不超过两次"是一条硬规则。** 连续三次追问的体验极差，用户会直接放弃语音、永久转向物理按键——这是最贵的失败，因为它损失的不是一次交互，是一个用户对整个功能的信任。

### 第二层：理解侧兜底 —— 防止编造和越权

- **能力边界白名单。**
	模型输出的意图必须落在已注册的意图表内。生成了一个不存在的意图，直接判定为不支持，走"我做不到"的话术，而不是尝试最接近的那个。 **"猜一个最接近的"是幻觉的主要来源。**
- **槽位强类型校验。**
	温度必须在 16 到 32 之间，音量 0 到 100。超出范围不裁剪、不静默取最近值，而是回问——因为超范围往往意味着理解错了。
- **知识问答强制引用。**
	车辆知识必须来自 RAG 检索结果，检索不到就说不知道，并给出售后入口。 **绝不允许模型凭参数记忆回答"你的车能不能拖挂"这类问题** ，答错的后果是实车损坏。
- **危险意图拦截。**
	行车中"打开后备箱""解锁车门""关闭安全带提醒"等意图，在网关层直接拒绝，理由明确告知用户。这一层在 Master 内，不下发到域。

### 第三层：执行侧兜底 —— 幂等、超时、回滚

![图片](https://mmbiz.qpic.cn/sz_mmbiz_png/Il8Q58ED4HNia9Yn6TXxXpUSsP9W1g91MibyAYvF6aWxzj2gFS0OF9HdYbLDiaOPEgEDxsKEh7vKdPf0RBJssQwKCC3FiaEpAdmDmb60HvOzFXY/640?wx_fmt=png&from=appmsg&watermark=1#imgIndex=9)

最危险的状态不是失败，是"部分成功且用户不知道"

"半个影院模式"这类中间态是投诉重灾区——用户不知道系统处在什么状态，也不知道该怎么恢复。所以宁可完整回滚到原状态，也不要停在中间。 **如果连回滚都失败了，必须主动、明确地播报当前状态，并提供一键复位** 。沉默是最糟糕的选择。

### 第四层：Master 自身兜底 —— 中枢也会挂

这一层最容易被忽略： **大家都在设计"子 Agent 失败怎么办"，很少有人设计"Master 自己失败怎么办"** 。但中枢一挂，整车智能全部失效，这是最严重的单点故障。

| Master 故障模式 | 检测方式 | 兜底路径 | 用户感知 |
| --- | --- | --- | --- |
| 大模型服务不可用 | 健康检查 + 熔断器 | 切换到端侧规则引擎，只支持高频指令表 | 复杂对话不可用，车控语音全部正常 |
| Master 进程崩溃 | 看门狗心跳 | 秒级重启 + 从持久化恢复会话上下文 | 短暂无响应，上下文保留 |
| 意图理解质量突降 | 线上置信度分布监控告警 | 自动回滚到上一模型版本 | 基本无感知 |
| 某域 Agent 持续失败 | 错误率熔断（滑动窗口） | 隔离该域，其余域正常，明确告知该能力暂不可用 | 局部功能不可用，其他正常 |
| 循环依赖 / 死锁 | DAG 深度限制 + 全局超时 | 强制终止任务链，返回已完成部分 | "这个我暂时没搞定" |

**那张"端侧规则引擎"的高频指令表是整套架构的最后保险。** 它必须覆盖 Top 200 高频指令（车控、媒体、导航基础操作、电话），纯本地、纯规则、不依赖任何模型。哪怕云端全挂、大模型全崩，用户说"打开空调"也必须有反应。 **这条底线是车规产品和互联网产品最本质的区别** ——互联网产品可以显示"服务暂不可用"，车不行。

### 第五层：体验侧兜底 —— 让失败也是好体验

技术兜底保证了系统不崩，体验兜底决定用户是否还愿意再用。三条原则：

1. **永远给反馈，绝不静默。**
	做不到就说做不到，超时就说在等。最差的情况是用户说完一句话，车没有任何反应——他不知道是没听见、在处理、还是失败了。
2. **说清楚"为什么"和"怎么办"。**
	"网络不好，充电站信息拿不到，要不我先按上次去过的那个导航？"这句话包含原因、影响、和一个可执行的替代方案。对比"操作失败"，成本几乎相同，体验差距巨大。
3. **失败必须留下可回收的路。**
	每次失败都提供下一步：换个说法、屏幕操作、转人工、稍后重试。 **把用户"卡在原地"是不可接受的** 。

怎么验证兜底真的有效：故障注入

兜底代码是最容易腐化的代码，因为它平时不执行，坏了也没人知道。唯一可靠的办法是 **在仿真环境和实车台架上主动注入故障** ：断网、云端 500、三方超时、模型返回非法 JSON、执行器无响应、Master 强杀。

我建议把这些注入用例做成 **发版必过的回归集** ，和功能用例同等地位。这件事的投入产出比在整个项目里是最高的——它把"我们有兜底"从一句 PPT 承诺变成了一条可验证的指标。

## 09怎么落地：三阶段，

不要一次性建 25 个 Agent，那是必然失败的路径

如果一家车企现在从零开始，我不会同时开工 25 个 Agent。 **正确的顺序是先把中枢和契约做扎实，再逐域接入** ——因为契约一旦定错，后面每接一个域都要返工一次。

| 阶段 | 做什么 | 验收标准（不达标不进下一阶段） |
| --- | --- | --- |
| 一期   中枢与契约 | Master 全部六大能力 + 消息总线 + 权限矩阵 + 座舱域 5 个 Agent + 端侧规则引擎兜底 | 车控意图准确率 ≥ 97%；端侧直达时延 P95 ≤ 500ms；断网时 Top 200 指令 100% 可用 |
| 二期   跨域打通 | 接入能源域、生态域，跑通跨域 DAG 编排、协商式关系、分段应答、五层兜底 | 三域复合意图完成率 ≥ 85%；跨域时延 P95 ≤ 1.6s；故障注入回归 100% 通过 |
| 三期   智驾与主动 | 接入智驾域（协商 + 上报）、运营域，开启主动服务四道闸门与数据闭环 | 主动服务接受率 ≥ 40%；关闭率 < 5%；安全事件让路成功率 100% |

三个阶段里， **最容易被压缩的是一期，而这恰恰是最不该压缩的** 。一期做的是看不见的东西——消息契约、权限矩阵、trace 体系、端侧兜底。它们在 demo 里毫无观感，但决定了二期三期能跑多快。压缩一期换来的时间，会在二期以三倍的返工量还回去。

### 组织上的两件事

架构问题往往是组织问题的投影。这套架构要落地，组织上必须解决两件事：

- **Master 必须有独立的团队和独立的 owner。**
	如果 Master 挂在座舱团队下面，它一定会长成"座舱的语音助手"，智驾和能源的能力永远接不进来——因为跨域协调需要的权限，座舱团队没有。
- **权限矩阵的变更权归安全团队。**
	第 04 章那个 `forbidden` 字段，必须由不承担功能交付 KPI 的团队持有。让赶排期的人自己审自己的安全边界，结果是可预期的。

## 写在最后：Master Agent 的本质是"责任的集中"

这篇文章讲了架构分层、Agent 清单、三种归属关系、消息契约、时延预算、优先级矩阵、五层兜底。如果只能记住一件事，我希望是这句：

> **Master Agent 的价值不在于它更聪明，而在于它把"理解用户"、"协调能力"、"承担失败"这三件事的责任集中到了一个地方。**

责任分散的系统里，每个模块都是对的，但整体是错的——每个团队都能证明自己的接口返回了 200，用户还是觉得这车不好用。责任集中的系统里，有一个地方对最终体验负责，也有一个地方在出问题时可以被追溯、被修正、被改进。

对中国新能源车企来说，这件事有额外的意义。硬件的堆料竞赛已经接近尾声，芯片算力、屏幕数量、传感器配置正在快速趋同。 **接下来真正的分水岭，是同样的硬件上，谁能把能力组织得更好** 。而组织能力的载体，就是这套调度架构。

它不好看，不适合放在发布会 PPT 的第一页。但它决定了三年后你的车是越用越懂用户，还是越用越让人失望。

本文是一份架构方法论，不针对任何特定车型或公司。文中的时延预算、优先级得分、指标目标均为工程建议值，实际项目需按平台算力、供应商能力和法规要求重新标定。

如果这篇对你有用，欢迎转发给正在做整车智能架构的同事。有不同意见的部分，尤其欢迎在评论区讨论——特别是第 04 章那三种归属关系的划分，和第 08 章第四层"Master 自身兜底"，这两块我认为是行业里讨论得最不充分的地方。
